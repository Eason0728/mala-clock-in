## 0. 一句話

主管在營運系統核定頁按「認定曠職」→ 營運系統伺服器補上**已發布班表**的事實（`kz_sched`）→ 用既有的 `mgr_approve`
送打卡端，內容是「那天 0 個上班時段＋假別曠職」。打卡端自己再驗一次（打卡、單據、期限、組合），通過才寫
「核定 0 小時＋leave 一列 曠職（時數＝班表時數）」。之後薪資、績效、鎖月全部看 leave 分頁那一列。

## 2. 認定曠職：營運系統 → 打卡端

### 2-1 動作與參數

沿用 `mgr_approve`（只檢查用 `mgr_approve_check` 的 items 一樣可以帶，打卡端照同一套檢查、不寫）。
沿用既有的寫回簽名（`DUTY_AUTH`／`wb_*`）、版本（`base_ver`）、待審鎖、鎖月檢查，**不新增動作名稱**。

```jsonc
{
  "action": "mgr_approve",
  "mgr_key": "<營運系統代管的主管鑰匙>",          // allow_acting=TRUE 那把
  "acting_name": "<按的人，管理系統姓名>",        // 必填：只收個人帳號代轉（第 2 題＋第 1 題「誰按的有紀錄」）
  "date": "2026-12-03",
  "emp_id": "MZTJS07",
  "base_ver": "<既有>",
  "periods": [],                                   // 一定要空
  "leaves": [{ "type": "曠職", "hours": 8 }],      // 一定只有這一種；hours 打卡端不採用（以 kz_sched.hours 為準）
  "kz_sched": {                                    // 營運系統伺服器讀資料填；前端送的一律蓋掉（同 sched_day 的做法）
    "work":   true,   // 已發布班表那天是「上班」（含出差班；不含休息日排班、國定假日；第 3-6 題排除名單的人日一律 false）
    "hours":  8,      // 已發布班表那天的班表時數（各段合計扣休息），0 < hours ≤ 24
    "xpunch": false,  // 這位同仁「其他打卡帳號」那天有沒有任何打卡（同一人跨帳號，認人同考勤提醒 ident.resolve）
    "xreq":   false   // 其他帳號那天有沒有待審或已核准的請假／出差／忘打卡單、或請假出差登記、或核定
  },
  "sched_day": "...", "sched_spans": [], "sched_ft": false, "sched_support": null, "sched_home": ""   // 既有，照舊帶
}
```

- `kz_sched` 只有個人帳號代轉（`reqMgrActing_` 為真）才採信；門市登入、舊值班頁（manager.html）不採信。
- `kz_sched` 形狀不對（缺欄位、型別不對、hours 不在範圍）＝無法確認是上班日 → 回句 11。
- `work` 是營運系統的責任：已發布（第 3-5 題 A）、出差班算、休息日排班不算（3-1 A）、國定假日不算、3-6 排除名單
  （到職前離職後、借到別店、支援帳號列、總部「同仁」開關關掉、總部起用日前、總監層級、被藏起來的總部支援列、
  瑞光文心 2027-01-01 前）都要給 `false`。打卡端另外自己擋：瑞光、文心（`CONFIG.PAYROLL_STORE` 為 `MZTRG`／`MZTWX`）2027-01-01 前一律句 11。

### 2-2 打卡端的檢查順序與回應（訊息逐字＝逐句表）

先跑既有的：主管鑰匙 → 核定人姓名 → 日期格式 → **鎖月（`pay_locked`）** → 名冊 → 遲到分鐘格式。
**開關關、或日期早於生效日**：完全不進下面這段，照今天的流程走（曠職不在白名單 → `{ok:false, error:'bad_leave_type'}`，前面有待審單就先回 `pending_request`，跟今天逐字一樣）。
開關開、日期 ≥ 生效日、請求帶了曠職，依序檢查（程式：`Code.gs kzApprovePre_`、`kzApprovePost_`）：

| 順序 | 條件 | 回應 |
|---|---|---|
| A | `leaves` 裡有 `曠職`，同時還有別的假別、或 `periods` 不是空的 | `{ok:false, error:'kz_mixed', message:句13}`；曠職選兩次＝既有 `dup_leave_type`「同一個假別選了兩次：曠職」 |
| B | 不是個人帳號代轉（門市鑰匙、沒帶 acting_name） | `{ok:false, error:'bad_leave_type'}`（＝今天的回應，沒有 message） |
| C | `kz_sched` 不採信／形狀不對／`work!==true`／瑞光文心上線前 | `{ok:false, error:'kz_not_workday', message:句11}` |
| E | 本店 requests 那天有待審或已核准（沒作廢）的 請假／出差／忘打卡單，或 `kz_sched.xreq===true` | `{ok:false, error:'kz_has_req', message:句10}` |
| （既有） | 那天還有其他待審單（例：加班單） | 既有 `pending_request`「這天還有待審的申請，請先審單（審完才能核定）」 |
| D | 本店 events 那天有任何一筆（不分狀態；隔天 06:00 前的下班卡算前一天），或 `kz_sched.xpunch===true` | `{ok:false, error:'kz_has_punch', message:句9}` |
| F | 那天已經有核定紀錄、或 leave 分頁那天有任何一列（含已認定的曠職；同一天按第二次也是這個） | `{ok:false, error:'kz_day_done'}`（**沒有 message**：逐句表沒有這句，見第 9 節待決） |
| G | 還在同仁自補期限內：`今天 ≤ 日期＋4 天`（同 `Requests.gs reqPastLimit_`，含未來日期） | `{ok:false, error:'kz_too_early', message:句12, until:'YYYY-MM-DD'}`，句 12 的 {日期}＝`until` 寫成 `M/D` |

之後照既有流程走（綁單檢查、只檢查停在這裡、鎖內重讀待審、寫入）。綁單檢查（`reqBindCheck_`）
對這一筆的「登記了曠職、沒有已核准的假單」不擋（只有通過上面檢查的曠職才豁免）。

成功：
```jsonc
{ "ok": true, "date": "2026-12-03", "emp_id": "MZTJS07", "name": "…", "periods": [],
  "approved_hours": 0, "leaves": [{ "type": "曠職", "hours": 8 }], "leave_type": "曠職", "leave_hours": 8,
  "status_text": "全天請假", "manager_name": "<acting_name>", "entered_at": "<ISO>", "dup_ignore": [],
  "kz": { "hours": 8 },
  "message": "已認定 12/3 曠職（8 小時）" }   // 句 8，{日期}＝M/D、{N}＝時數（最多 2 位小數、去尾 0）
```
只檢查（`dry_run`）成功：照既有 dry_run 形狀，另帶 `kz:{hours}`，不帶 message。

### 2-3 寫進資料的樣子（第 5 題 A）

- `approved`：一列，periods 空、approved_hours 0、status_text `全天請假`（**資料上的狀態字不新增**，避開 kickoff 第 5 題 B 的風險）、
  manager_name＝acting_name、entered_at＝現在。
- `leave`：同日同人既有列全刪，加一列 `[日期, 姓名, '曠職', 班表時數]`。
- 畫面要顯示「曠職」不是「全天請假」：看 leave 那天假別是 `曠職`（句 15）。本分支已做：
  打卡頁「最近 40 天」（`my_recent` 把那天列出來、`approved_status:'曠職'`；九店頁面不用改）、
  LINE 出勤班表（`line_hub_sched` 那天帶 `kz:true`，`sched-line.js` 點那天多一行「曠職」）。
  營運系統核定卡、完整核定頁（第二階段）照 leave 判斷。句 14 的 {日期} {職稱}：用 approved 的 entered_at、manager_name，職稱由營運系統查。
- `mgr_day`（v1.2）：那位同仁那天 leave 有 `曠職`、而且開關開、日期 ≥ 生效日時，`approved` 物件**最後**多一欄 `entered_at`（核定列的時間，台北 ISO，`normCellTs`）。
  其他情況（沒有曠職、別的假別、開關關或壞值、日期在生效日前）回應逐字不變。程式：`Code.gs handleMgrDay`。
  連帶：`with_ver` 的版本（`DutyFeed.gs dutyVerOf_` 把 approved 整份算進去）只有「那天有曠職登記」的人會不同；沒曠職的人、開關關都不變。
  上線順序上開關在九店與快速通道都換新程式之後才開，開之前沒有任何曠職登記，所以不會有新舊程式算出不同版本的空窗。

### 2-4 改判（第 12 題 A）

能核那天的人重新核定那天（改成請假、出差、上班時段或刪掉）＝既有 `mgr_approve` 覆蓋，leave 那天整批換掉 → 曠職消失、扣款歸 0。
不做撤銷按鈕。重新核定時**不要**再帶 `曠職`（帶了會走上面整套檢查，而 F 會擋）。
「補單打回」（mala-clock-in PR #241）若上線：核准補單把那天打回待核定時，曠職跟著消失（測試裡留了情境說明）。

### 2-5 一般假別下拉、同仁請假單、代開都選不到

- `payroll_leave_options` 回應的 `types` 一律不含曠職（開關開也一樣）→ 營運系統完整核定頁、打卡端主管頁、LINE 額度卡都看不到。
- `leaveTypeAllowedByPayroll('曠職')` 一律 false → 一般核定（非上面那條路）回 `bad_leave_type`、主管代開回 `bad_leave_type`。
- 同仁 LINE 請假單：白名單 `LEAVE_TYPES` 沒有曠職，回 `bad_leave_type`。
- 第二階段：完整核定頁顯示既有的曠職那天時，下拉要能「顯示」曠職（唯讀），但不能讓人選；重新核定時不要把它當一般假別送回。

## 3. 疑似曠職：誰算、怎麼對齊

| 用途 | 誰算 | 資料 |
|---|---|---|
| 薪資頁提醒（句 16、19）、鎖月擋（句 22） | 打卡端薪資（光復 `Payroll.gs payKzScan_`） | 已發布班表 sched_pub、國定假日清單（不含選舉日）、本店 events／approved／leave／requests、同品牌支援的核定時數 |
| 核定卡的標籤、按鈕灰／可按（句 1–4） | 營運系統（第二階段） | 營運系統自己的已發布班表、考勤副本 |
| 每天 08:50 行政群 | 營運系統 `absent-sched.js`（第二階段改成只看已發布、排除國定假日與 3-1、瑞光文心） | 同上 |
| 認定當下的最後把關 | 打卡端 `handleMgrApprove`（第 2-2 節） | 本店資料＋營運系統帶的 `kz_sched` |

- 兩邊**不互相拿清單**；一致靠「同一個判定函式＋同一份案例檔＋同一個生效日」：
  - 判定函式正本：`apps-script/Code.gs` 的 `kzSuspect_(f)`（純函式，不碰試算表）。營運系統逐字搬一份到自己的檔
    （建議 `server/kuangzhi-rules.js`），不得改條件。
  - 案例檔：`tests/fixtures/kuangzhi-cases-v1.json`（兩個 repo 放同一份，測試釘 sha256，要改兩邊一起改）。
  - 自補期限：`kzSelfUntil_(date)`＝日期＋4 天（含）；`kzCanMark_(date, today)`＝今天 > until。案例檔一起涵蓋。
- `kzSuspect_(f)` 的輸入（每一項由各端用自己的資料填）：

| 欄位 | 意思 |
|---|---|
| `work` | 已發布班表那天是上班（含出差班；不含休息日排班） |
| `hol` | 那天是國定假日（不含選舉日）。v1.3：以**營運系統節日表**為準＝`server/kuangzhi.js isHoliday`（`holidays.json` 的 `days`：節日當天、含週末；＋`gov.off`：平日放假、含補假與調整放假）。營運系統直接用；打卡端薪資＝自己的國定假日清單**或**已發布班表那格 `x='hol'`（第 3-1、3-1b 節） |
| `punch` | 那天有任何打卡（不分狀態；隔天 06:00 前的下班卡算前一天；跨帳號同一人都算） |
| `approved` | 那天有核定紀錄（含核定 0 小時）或支援別店有核定時數 |
| `leave` | leave 分頁那天有任何一列（含曠職、出差、時數空白） |
| `req` | 待審或已核准、沒作廢的 請假／出差／忘打卡單（加班單不算） |
| `excluded` | 第 3-6 題排除名單。打卡端薪資＝瑞光文心 2027-01-01 前（自己看得到）**或**已發布班表那格帶有效的排除代號 `x`（第 3-1 節，營運系統判）；在職日由掃的日子本身限定（到職～離職）。營運系統＝自己判全部 |
| `date`、`from`、`until` | 日期要 ≥ 生效日、≤ 計算截止日（月中草稿＝昨天） |

  → `work && !hol && !punch && !approved && !leave && !req && !excluded && date ≥ from && date ≤ until`。
- 已認定的曠職：leave 那天有一列 `曠職` → `leave` 為真 → 自然不再是疑似（行政群也不再列）。

### 3-1 排除代號 `x`（v1.2，兩端共同定義）

薪資端看不到的排除項（總監層級、總部「同仁」開關關掉、支援帳號列、瑞光文心上線前）由營運系統在**發布班表**時標在那一格，薪資讀它本來就讀的已發布班表。

| 項目 | 約定 |
|---|---|
| 位置 | `sched_publish` 的 `rows[].cells[]` 一格，選填欄 `x`；不改 `t`／`s`／`l`／`w`，不改版本號 `v` |
| 值 | 字串，只認五個：`dir`（總監層級）、`hq_off`（總部「同仁」開關關掉）、`away`（支援帳號列）、`late`（瑞光文心 2027-01-01 前）、`hol`（v1.3：營運系統節日表的國定假日，第 3-1b 節） |

### 3-1b 國定假日 `hol`（v1.3，2026-11-27，兩端共同定義）

- 主管定案（選 A）：**節日當天與補假日都不記曠職；兩邊以營運系統節日表為準。**
- 起因：薪資國定假日清單（`payroll_holiday` 的 dates，`Payroll.gs payHolidayDoublePlan`；營運系統推送的 `payrollRows` 同一套規則）把週末節日配到補假日：
  2027-02-06（六）、02-07（日）、02-28（日）不在清單、對應的 02-09、02-10、03-01 在；營運系統節日表兩種都有 → 同一天營運系統不列疑似、不能認定，薪資卻列疑似。
- 營運系統（`server/kuangzhi.js pubExcl`）：`late` → `away` → `hq_off` → `dir` 都不是時，`isHoliday(日期)` ＝真 → `x='hol'`（排最後：已經有別的原因的格子代號不變，不會多重送）。
  其他條件同第 3-1 節（開關開、日期 ≥ 生效日、格子是 W；開關關一格都不帶）。核定卡疑似、認定曠職 `kz_sched.work`（`schedFacts`）、每天提醒（`digestKeep`）本來就用同一支 `isHoliday`。
- 打卡端：`Code.gs KZ_PUB_X_` 多認 `hol`（收發布、薪資掃疑似都經 `kzPubX_`）。`Payroll.gs payKzScan_` 程式不變：有效 `x` ＝不列疑似、連續天數照「別的上班日」斷開（跟薪資清單裡的國定假日結果相同）。
- 薪資自己的清單照留（只會多排除、不會少）：清單的加發日＝平日節日＋補假＋沒配到補假的週末節日，都在營運系統節日表裡；
  唯一可能多出的是 `payroll_holiday` 的「本店專屬」列（有沒有這種列**未確認**）。
- **不影響**：國定假日加發（`ot_hol`）、紅字天數、底薪、加班日別、選舉日、國定假日調移、補休——全部照薪資自己的清單，跟 `x` 無關（測試 kuangzhi-x 第六節 H5 釘住）。
- 兩邊生效日要同一天：營運系統只在日期 ≥ 自己的 `KUANGZHI_FROM` 帶 `hol`；打卡端若比較早開，中間的週末節日薪資仍會列疑似。
- **上線一定要做（v1.3）**：①兩邊 `KUANGZHI_FROM` 設**同一天**（打卡端九店＋光復的指令碼屬性、營運系統 `server/.env`）。②開關打開、營運系統部署完成（重啟後）**一定要手動跑** `node server/tools/kz-resend.js`（只檢查，看清單）→ `node server/tools/kz-resend.js --go`（重送）→ 再跑一次只檢查應全部「內容已一樣」。不重送的話，改版前已送出的舊班表沒有 `hol`：2027-02-06、02-07、02-28 有人排 W 沒來會被薪資**誤列疑似**（營運系統那天又不能認定）。重送完才開 `KUANGZHI_LOCK_BLOCK`。
- 節日表改版（匯入新版 `holidays.json` 並部署營運系統）後，已送出的期 `hol` 可能跟著變 → 照第 3-1 節的重送流程跑 `server/tools/kz-resend.js`（只檢查 → `--go`），沒有自動觸發。

## 7. 扣薪（第 6 題，主管 2026-11-26 定案）

- 主管原話：「第六題，使用全薪÷ 30 × 曠職天數」；兩點細節回「都照建議」：全薪＝跟事假扣款時薪同一組（底薪＋職能＋夜間＋店長加給＋績效上限）、
  半天班按班表時數比例。既有做法（主管沒異議）：金額最後四捨五入到元、月中到職不折算。
- **曠職天數**＝每個認定曠職的日子「那天的班表時數（leave 分頁曠職那列的時數）÷ 每日基本工時（參數 `daily_hours`，預設 8）」，單日最多 1 天，當月加總。
- **扣款**＝全薪 ÷ 30 × 曠職天數，最後一步才四捨五入到元（不先把每天金額取整）。全薪＝`Payroll.gs payLeaveFullPay_(e)`（請假扣款時薪用的同一支，未折算）。
  例（全薪 34,000）：8 小時 1 天 1,133；4 小時 0.5 天 567；3 天 3,400；8＋4 小時 1.5 天 1,700；9 小時也是 1 天 1,133。
- 唯一計算處：`Payroll.gs payKzDeduct_(e, ym, days, cfg)`，天數在 `payKzDays_`。一般假別扣款不套到曠職，假別表的「給薪比例」改了也不影響金額。
- 計時（全薪 0）：照印一列、金額 0（第 6-4 題）。不連帶扣例假、休息日（第 6-3 題）。
- 薪資單扣款列名稱：常數 `PAY_KZ_LABEL = '曠職(無薪) {N}天'`（逐句表句 21 的 H 換成天，大腦正在請主管確認；{N} 顯示到小數一位、整數不帶小數點）。
- 佔位旗標已拿掉；`tools/kuangzhi-release-check.js` 改成檢查「旗標不存在」（又出現就結束碼 1）。上線清單仍建議先跑它。
