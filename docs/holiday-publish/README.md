# 薪資接收營運系統推送的節日表（節日表只留一份，第 2 個改動）

2026-11-24 主管裁示：「整個系統只會有一份節日表，節日表的日期都是參照行政院人事處頒布的行事曆」。
正本放在營運系統（mala-store-ops `server/holidays/master.json`，人資主管確認後生效，見該 repo `docs/holidays/README.md`）。
這份文件寫的是**薪資這一端**：怎麼收營運系統推過來的「每月紅字天數＋國定假日加發日」，以及開關、退回、鎖月與本店專屬的處理。

| 改動 | 內容 | 狀態 |
|---|---|---|
| 1 | 營運系統：節日正本、匯入工具、比對清單、每天檢查燈號 | mala-store-ops 草稿 PR #396 |
| 2 | 薪資：接收推送＋開關（本文件） | 這個 PR |
| 3 | 營運系統：試推、每天推送給薪資 | 未做 |
| 4 | 門市排班改認補假日 | 未做 |

**薪資怎麼算一行沒改**：讀 `payroll_holiday` 分頁的函式（`payHolidayRow`、`payHolidayDates`、`payRedDaysCheck_`、`payCollect`、`payOtKindOf`、`payHolMoved_`、補休帳、損益估算…）一個字都沒動，只換分頁的資料從哪裡來。

## 1. 開關 `PAY_HOL_SOURCE`（光復專案指令碼屬性）

| 值 | 行為 |
|---|---|
| 沒設、`gov`、空白、其他任何值 | **現行做法**（預設）：薪資頁打開就在背景叫 `payroll_holiday_sync` 向人事行政總處抓「今年」行事曆寫分頁；算薪時該月沒有列也會先抓一次。跟改版前逐步相同（`tests/hol-publish-equiv.test.js` 對照）。 |
| `mini`（不分大小寫、前後空白不算） | **只收營運系統推送**：薪資頁打開、算薪都**不再連人事行政總處、也不再自動寫**分頁；缺資料時明確提示（下表）。 |

只收推送時三個既有動作的變化：

| 動作 | 只收推送時 |
|---|---|
| `payroll_holiday_sync`（薪資頁打開時背景呼叫） | 不連外、不寫分頁；回分頁現況（同原本的 `holidays`）＋`hol_source:'mini'`、`hol_pub`（收到的版本）、`hol_missing`（要的年份裡缺的月份）。`message` 在「還沒收到任何一版」或「缺本月」時說明。畫面在紅字天數表上方多一行版本。 |
| `payroll_calc` 該月沒有列 | 不自己同步，回 `no_holiday`：「薪資計算（2028-01）：還沒有這個月的節日資料，這次沒有計算。請先到營運系統確認並發布 2028 年節日表，再重新計算。」（不會當成沒有節日；有列時跟以前完全一樣） |
| `payroll_holiday_set`（手動整批覆寫，集團或本店專屬） | 擋下 `hol_source_mini`：「節日表現在由營運系統發布，薪資這邊不能手動改紅字天數或國定假日；要改請到營運系統確認並發布新版。」（第 4 題：本店專屬不再接受新的；集團列只能由營運系統發布） |

**黃燈決定**：`payroll_holiday_sync` 在只收推送時**擋下**（不連外、不寫），不保留給緊急手動。理由：薪資頁每次打開都會自動呼叫它，分不出「自動」和「緊急手動」；緊急時的做法就是退回（把開關改回 `gov`），那一刻起舊同步立刻恢復。

**退回**：把 `PAY_HOL_SOURCE` 刪掉或改成 `gov`，下一個請求就回到現行做法（每次請求當場讀屬性）。分頁內容不用搬：推送寫的格式跟同步寫的一模一樣（同樣的 5 欄、同樣的集團列）。

`payroll_gov_holidays`（管理者手動看人事行政總處行事曆，唯讀）不受開關影響；薪資頁沒有呼叫它。

## 2. 推送動作 `payroll_holiday_publish`

### 2-1 請求

```
POST（text/plain JSON，跟其他 payroll_* 一樣）
{
  "action": "payroll_holiday_publish",
  "svcKey": "<指令碼屬性 PAY_HOL_SVC_KEY>",
  "v": 1,
  "version": "2027-3",                         // 營運系統正本 load().version（西元最後一年-第幾版）
  "published_at": "2026-12-01T06:10:00+08:00", // 這一版確認／發布的時間（含時區）
  "confirmed_by": "人資主管",                  // 選填，40 字內（寫職稱）
  "source": "人事行政總處 116 年辦公日曆表（2026 年 7 月版）",   // 選填，200 字內
  "rows": {                                     // 營運系統 payrollRows(master).rows，整年 12 個月為單位
    "2027-02": { "ym": "2027-02", "red_days": 13, "note": "依人事行政總處116年…", "dates": "2027-02-04, 2027-02-05, 2027-02-08, 2027-02-09, 2027-02-10" },
    …
  },
  "moved": { "2027-02-06": "2027-02-09", … },   // 選填，payrollRows().moved；只給畫面標「替哪天補假」
  "names": { "2027-02-09": "補假", … },          // 選填，正本每個有備註的放假日；只給畫面顯示節日名稱
  "dry_run": true,                              // 選填；true＝試推，只回報不寫
  "reapply": true                               // 選填；同版本重送時把分頁對齊這一版（見 2-3）
}
```

- 金鑰：專用的 `PAY_HOL_SVC_KEY`，沒設＝全部拒絕（`unauthorized`）；管理金鑰不能用。帶 `scope`（門市範圍）一律 `scope_forbidden`。
- `PAY_HOL_SOURCE` 不是 `mini` 時**只接受試推**；正式推送回 `hol_source_gov`、不寫。

**黃燈決定**：用新的專用金鑰，不沿用考勤提醒的 `ATT_ALERT_SVC_KEY`（`payroll_comp_period` 用的那把）或排班的 `SCHED_SVC_KEY`。理由：那兩把現在只能讀或只能寫班表，拿來寫薪資節日會擴大它們能做的事；專用金鑰沒設就等於這個動作不存在。代價是上線要多設一個屬性（營運系統那邊放同一把）。

### 2-2 內容檢查（不合格整份拒收，分頁一格不動）

回 `{ok:false, error:'bad_payload', problems:[…最多 20 條], message}`，`message`：「節日表推送內容不合格，整份沒有收（薪資的節日資料沒有變動）：…」。檢查項目：

| 類別 | 規則 |
|---|---|
| 版本 | `v` 是 1；`version` 是「西元年-第幾版」（第幾版 ≥ 1）；版本的年份＝內容最後一年 |
| 時間 | `published_at` 是含時區的時間 |
| 空表／半套 | `rows` 是以月份為鍵的物件、不能是空的；每一年都要整年 12 個月；年份連續不能斷；一定要有今年；最多 240 個月 |
| 每一列 | 只能有 `ym`、`red_days`、`note`、`dates`（`store` 只能沒有或空白）；`ym`＝鍵；`red_days` 是整數；`dates` 是 `""` 或「YYYY-MM-DD, YYYY-MM-DD」（逗號加一個空白），每天都存在、都在這個月、由小到大不重複；加發日天數 ≤ 紅字天數；國定假日加發生效（2026-08）之前的月份 `dates` 要空白 |
| 本店專屬 | 任何一列帶了門市（`store` 有值）→ 拒收（第 4 題：本店專屬不再接受新的） |
| 天數合理 | 每月紅字天數在「該月週末天數 −3 ～ ＋9」之內（且不超過當月天數）；每年合計 105～130 天 |
| 顯示用 | `moved` 是 {日期:日期}（最多 400 筆）、`names` 是 {日期:40 字內文字}（最多 1000 筆） |

**黃燈決定（門檻）**：每月「週末 −3～＋9」、每年 105～130。依據：106～116 年原檔每年放假 115～121 天；補行上班最多讓一個月少 1～2 天、春節連假最多讓一個月比週末多 7 天（2023-01）。比營運系統匯入端的「內容可疑」門檻寬，只擋明顯錯的內容；真正的把關在營運系統的比對清單與人工確認。

### 2-3 版本與冪等

目前生效的版本記在指令碼屬性 `PAY_HOL_PUB`（版本、內容指紋、發布時間、確認人、收到時間、年份）。

| 情況 | 結果 |
|---|---|
| 第一次收、或版本比目前新 | 套用（2-4）、記一筆稽核、記新版本，回 `added:true` |
| 版本比目前舊 | `version_rollback`，不寫 |
| 同版本、內容不同 | `version_conflict`，不寫（同一版本不能改內容，要營運系統升版） |
| 同版本、內容相同 | **不寫任何東西**，回 `added:false`；`drift` 列出分頁跟這一版不同的月份（例如有人退回舊同步後又切回來） |
| 同版本＋`reapply:true` | 照 2-4 的規則把分頁對齊這一版、記稽核「重新套用」、版本紀錄不變 |

指紋只看每月的 `ym`、`red_days`、`dates`、`note`（`moved`、`names` 只是畫面用）。

**黃燈決定**：同版本重送時分頁不同只回報 `drift`、不自動改回。理由：「同一版本重送不重寫」，避免每天推送默默蓋掉別的管道的改動；要對齊就明確帶 `reapply:true`。

### 2-4 寫哪些月份（規則白話）

推送只動 **集團共用列**（`store` 空白），照 `payHolidaySync` 原本的保護：

1. 2026-05（薪酬系統第一個月）以前的月份忽略，不建列。
2. **本月與未來**的月份：分頁那格跟推送不同（紅字天數、加發日，或紅字天數空白／不是數字）→ 改成推送的；沒有那個月 → 新增。說明欄（note）不同不算不同。
3. **已經過去的月份一律不動**：內容不同列在 `skipped_past`，缺列列在 `past_missing`，都不寫（第 9 題）。
   這一點比原本的同步更保守：原本同步會「補」缺的過去月份；推送不補。
4. **已鎖定**：某個月只要有「用集團列的門市」已鎖定（`payroll_run` 有 `final`），那個月不改也不補，列在 `skipped_locked`（同 `payHolidaySyncLockedYms_`）。該月有本店專屬列的門市不吃集團列，不算。
5. **本店專屬列**（`store` 有值）一律不碰、也不拿來跟推送比；回應 `own_rows` 是分頁上本店專屬列的筆數。
6. 寫入在寫鎖內（`payWriteLocked_`，鎖內重讀分頁與鎖定狀態）；分頁整張寫一次（`payReplaceAll`，有寫入防壞與還原）；稽核一筆 `holiday_publish`；最後才記版本。拿不到寫鎖回 `busy`、什麼都不寫。

### 2-5 回應

```
{ ok:true, mode:'mini'|'gov', dry_run:false, version:'2027-3', current:'2027-2'（收之前的版本，沒有＝''）,
  added:true|false,                 // 這次有沒有記成新版本（試推＝會不會）
  months_new:[…], months_changed:[…], skipped_locked:[…], skipped_past:[…], past_missing:[…], own_rows:0,
  changed:[…]                       // 正式推送：實際寫的月份（新增＋改）
  would_change:[…]                  // 試推：會寫的月份
  drift:[…]                         // 只有同版本重送、沒帶 reapply 時才有
}
```

錯誤：`unauthorized`、`scope_forbidden`、`bad_payload`、`hol_source_gov`、`version_rollback`、`version_conflict`、`busy`。

稽核（`payroll_audit`）一列：`action='holiday_publish'`、`operator='mini'`（有確認人時「mini（人資主管確認）」）、`reason` 例：
「營運系統節日表 版本 2027-1（發布 2026-11-24T20:52:47+08:00）：新增 2027-01、…、2027-12；已鎖定跳過 2026-12；已經過去的月份不動 2026-10」。

## 3. 本店專屬列（第 4 題）

- 現況：`payroll_holiday` 分頁 `store` 欄有值的列＝該門市專屬，**同一個月優先於集團列**（`payHolidayRow`：先找本店、沒有才用集團；`payHolidayList` 標 `_src:'own'`）。原本只能用 `payroll_holiday_set`（帶 store）寫。
- 這次：推送不接受也不碰本店專屬列；只收推送時 `payroll_holiday_set` 擋下 → 不再有新的。已存在的照舊優先、不動（已發的薪資不會變）。
- 唯讀列出：`{action:'payroll_holiday_own_list', admin_key}` → `{ok, count, rows:[{ym, store, red_days, dates, note, global_red_days, global_dates, same_as_global}]}`（只讀分頁、不讀不寫屬性；帶 scope 一律擋）。給主管看哪些店、哪幾個月有自己的設定、跟集團列一不一樣。
- 開關在預設值時 `payroll_holiday_set` 照舊可用（跟主線相同）；「不再接受新的」從切到只收推送那一刻起生效。
