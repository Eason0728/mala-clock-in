## 1. 這次改了什麼

- **薪資的計算公式沒改**：國定假日加發、基本工時（紅字天數）、補休、加班的算法一個字都沒動。
- 改的是**紅字天數與國定假日從哪裡來**：以前薪資頁一打開就自己去人事行政總處抓今年的行事曆；改成由營運系統的節日表送過來（那份是人資主管確認過的）。
- 另外多一個擋下：切到「只收營運系統」之後，算薪時如果那個月沒有節日資料，**直接擋下不算**並說明原因（以前會先自己去人事行政總處抓一次）。不會把「沒有資料」當成「這個月沒有國定假日」。
- **現行做法也改一點**（主管 2026-11-25：「甲，也套用」）：**已經過去的月份**整月沒有節日資料時，不再自動去人事行政總處補；那個月按計算會被擋下、顯示沒有節日資料，要人工在節日表（薪資試算表的 `payroll_holiday` 分頁）補上才能算薪。本月與未來的月份照舊自動帶入。正式環境 2026-05 以後每個月都有資料，正常看不出差別。

## 2. 兩種做法（由資訊部切換）

| 做法 | 什麼時候 | 薪資頁看到什麼 |
|---|---|---|
| 現行做法（預設） | 上線後先維持這個 | 跟現在一樣；只差在**已經過去的月份缺了不再自動補**（第 3 節） |
| 只收營運系統 | 營運系統試送沒問題後才切 | 紅字天數表上方一行版本；說明文字換新的；薪資這邊不能再手動改紅字天數 |

切回現行做法隨時可以，切完下一次操作就生效，資料不用搬。

## 3. 已經過去、已經鎖定的月份，與「本店專屬」設定

- **已經過去的月份**：營運系統送來的新節日表**一律不改**它們（主管第 9 題「全部凍結」）。連「那個月根本沒有資料」也**不補上**（主管 2026-11-25 定案原話：「過去的月份整月沒有節日資料時，不補上。」），**兩種做法都一樣**（主管 2026-11-25 問「現行做法的自動補要不要也套用」，原話「甲，也套用」）。
  - 「已經過去」＝早於台北時間的本月（主管原話「甲，照現有算法」）。例：12/1 00:00 起 11 月就算過去，12/1～12/10 結算 11 月時也一樣。
  - 後果一：如果某個已經過去的月份沒有節日資料，那個月**不能在系統裡算薪資**，按計算會擋下、顯示沒有節日資料；要**人工在節日表補上**（資訊部到薪資試算表的 `payroll_holiday` 分頁加那一列，系統外處理）才能算薪。系統本身沒有補上過去月份的方法：推送不補、開頁同步不補、算薪不補，**切回現行做法（`gov`）也不會補**。目前 2026-05 以後每個月都有資料，正常不會發生。
  - 什麼時候會發生：現行做法下，每個月的那一列是在「那個月還是本月」時，有人打開薪資頁或按計算才自動補上（薪資頁只帶今年；每年 1 月第一次打開補整年）。一整個月都沒人打開薪資頁、也沒人算薪，那個月過完就補不上了。每月 1～10 號結算時都會打開，所以正常不會發生。
  - 後果二：如果某個已經過去的月份跟新節日表不一樣，它會一直維持舊的內容（已發的薪資不會變）；版本行會列出這些月份。
- **已經鎖定的月份**：有門市用集團設定、而且那個月已鎖定，就不改那個月。
- **本店專屬設定**（某家店另外設的紅字天數與加發日，會優先於集團設定）：營運系統送來的內容不會動到它們；切到「只收營運系統」後不能再新增或修改；已經有的照舊生效，資訊部可以列出清單給主管看。

# 工程附錄（資訊部）

## A-1 開關 `PAY_HOL_SOURCE`（光復專案指令碼屬性）

| 值 | 行為 |
|---|---|
| 沒設、`gov`、空白、其他任何值 | 現行做法：`payroll_holiday_sync`（薪資頁打開時背景呼叫）向人事行政總處抓今年行事曆寫分頁；`payroll_calc` 該月沒有列也先同步一次。**差別（2026-11-25 主管「甲，也套用」）**：`payHolidaySync` 不新增已經過去的月份（月份 < `currentYmTaipei()`），回應多 `past_missing`、`message` 多一句；`payroll_calc` 該月是過去月份且沒有列 → 不同步、回 `no_holiday`＋`hol_past:true`＋跟只收推送同一句（`payHolPastNoRowText_`）。沒有過去缺列時跟改動前逐字相同（`tools/hol-gov-equiv.js`：d26637a 對本版 4 情境 × 4 種開關值 1616 步）、跟主線逐步相同（`tests/hol-publish-equiv.test.js`）。 |
| `mini`（不分大小寫、前後空白不算） | 只收營運系統推送（下表）。 |

> ⚠ **打錯字會悄悄停在現行做法**：例如打成 `min`、`mini2`、`mnii`，程式一律當成現行做法，不報錯（這樣設計是因為「不認得就退回舊做法」最安全）。切換後請確認：薪資頁紅字天數表上方出現「節日表版本…」那一行，或推送回應的 `mode` 是 `mini`。

只收推送時：

| 動作 | 行為 |
|---|---|
| `payroll_holiday_sync` | 不連人事行政總處、不寫分頁；只回分頁現況（`holidays`）＋`hol_source:'mini'`、`hol_pub`（版本、發布時間、`lag`＝沒跟上的月份）、`hol_missing`（要的年份裡缺的月份）、`message`。 |
| `payroll_master_get` | 多帶 `hol_source`、`hol_pub`、`hol_message`、`hol_missing`、`names`、`moved`、`double_from`（共用登入不呼叫 sync，靠這裡顯示版本行）。開關預設時回應不變。 |
| `payroll_calc` 該月沒有列 | 不同步；回 `no_holiday`。已經過去的月份另帶 `hol_past:true`、訊息請聯絡資訊部；本月或未來請營運系統發布。有列時跟以前完全一樣。 |
| `payroll_holiday_set` | 回 `hol_source_mini`、不寫（集團列與本店專屬都一樣）。 |

**黃燈決定**：只收推送時 `payroll_holiday_sync` 的實際行為是**不連外、不寫分頁、只回目前分頁內容與版本**（不保留給緊急手動）。理由：薪資頁每次打開都自動呼叫它，分不出自動或手動；緊急時把開關改回 `gov` 就恢復舊同步。

**退回**：`PAY_HOL_SOURCE` 刪掉或改成 `gov`，下一個請求就回現行做法。推送寫的分頁格式跟同步相同，不用搬資料。

`payroll_gov_holidays`（管理者手動看人事行政總處行事曆，唯讀）不受開關影響；薪資頁沒有呼叫它。

## A-2 推送動作 `payroll_holiday_publish`

請求（text/plain JSON）：

```
{
  "action": "payroll_holiday_publish",
  "svcKey": "<指令碼屬性 PAY_HOL_SVC_KEY>",
  "v": 1,
  "version": "2027-3",                         // 營運系統正本 load().version（西元最後一年-第幾版）
  "published_at": "2026-12-01T06:10:00+08:00", // 這一版確認／發布的時間（含時區）
  "confirmed_by": "人資主管",                  // 正式推送（含 reapply）必填、試推選填；40 字內（寫職稱）
  "source": "人事行政總處 116 年辦公日曆表（2026 年 7 月版）",   // 選填，200 字內
  "rows": { "2027-02": { "ym": "2027-02", "red_days": 13, "note": "…", "dates": "2027-02-04, 2027-02-05, …" }, … },   // payrollRows(master).rows
  "moved": { "2027-02-06": "2027-02-09", … },   // 選填，只給畫面
  "names": { "2027-02-09": "補假", … },          // 選填，只給畫面（正本每個有備註的放假日）
  "dry_run": true,                              // 選填：試推，只回報不寫
  "reapply": true                               // 選填：同版本時把分頁對齊這一版
}
```

- 金鑰：專用 `PAY_HOL_SVC_KEY`，沒設＝全部 `unauthorized`；管理金鑰不能用。比對用定時比較 `payHolCtEq_`（不論哪一字不同、長度差多少都跑滿較長那邊，Apps Script 沒有內建所以自己寫）；拒收回應只有錯誤碼與中文說明，不含金鑰、金鑰屬性名或任何網址。
- 確認人：正式推送（含 `reapply`）沒帶 `confirmed_by` 或空白 → `bad_payload`（`problems` 寫「正式推送要帶 confirmed_by」），整份不收（已定案「人資主管確認過的版本才生效」）。試推不用帶。錯誤碼沿用 `bad_payload`，營運系統已列為拒收不重送。
- 不寫的路徑（試推、同版本沒帶 `reapply`）與唯讀動作（`payroll_holiday_own_list`、只收推送時的 `payroll_holiday_sync`）**分頁不存在也不建**：用 `payReadNoCreate_`，不取寫鎖、不寫任何格子或屬性（分頁不存在＝當成沒有列，照樣算出預覽）。
- 帶 `scope`（門市範圍）：沒帶管理金鑰回 `unauthorized`（既有的防探測設計：先驗管理金鑰再守門，不讓人用回應探出資料）；帶了管理金鑰回 `scope_forbidden`。
- 開關不是 `mini` 時只接受試推；正式推送回 `hol_source_gov`、不寫。

**黃燈決定**：專用金鑰，不沿用 `ATT_ALERT_SVC_KEY`（`payroll_comp_period` 用）或 `SCHED_SVC_KEY`。那兩把現在只讀或只寫班表，拿來寫薪資節日會擴權；代價是上線要多設一個屬性（營運系統放同一把）。

### 內容檢查（不合格整份拒收 `bad_payload`，分頁一格不動）

| 類別 | 規則 |
|---|---|
| 版本 | `v`＝1；`version`＝「西元年-第幾版」（≥1）；年份＝內容最後一年 |
| 時間 | `published_at` 含時區 |
| 空表／半套 | `rows` 是以月份為鍵的物件、不能空；每年整年 12 個月；年份連續；一定要有今年；最多 240 個月 |
| 每一列 | 只能有 `ym`、`red_days`、`note`、`dates`（`store` 只能沒有或空白）；`ym`＝鍵；`red_days` 整數；`dates` 是 `""` 或「YYYY-MM-DD, YYYY-MM-DD」，每天存在、在這個月、由小到大不重複；加發日天數 ≤ 紅字天數；2026-08 以前 `dates` 空白 |
| 本店專屬 | 任何一列帶門市 → 拒收 |
| 天數合理 | 每月紅字天數＝該月週末天數 −3～＋9（≤ 當月天數）；每年合計 105～130 |
| 顯示用 | `moved` {日期:日期}（≤400）、`names` {日期:40 字內}（≤1000） |

**黃燈決定（門檻）**：106～116 年原檔每年放假 115～121 天；補行上班最多讓一個月少 1～2 天，春節連假最多讓一個月比週末多 7 天（2023-01）。只擋明顯錯的內容，真正把關在營運系統的比對清單與人工確認。

### 版本與冪等（版本記在指令碼屬性 `PAY_HOL_PUB`）

| 情況 | 結果 |
|---|---|
| 第一次收、或版本較新 | 套用、記稽核、記新版本＋這次沒跟上的月份（`lag`），`added:true` |
| 版本較舊 | `version_rollback`，不寫 |
| 同版本、內容不同（內容＝每月紅字天數＋加發日） | `version_conflict`，不寫 |
| 同版本、內容相同（只有說明 `note` 不同也算相同） | 不寫任何東西，`added:false`；`drift` 列出分頁跟這一版不同的月份 |
| 同版本＋`reapply:true` | 照下面規則對齊、記稽核「重新套用」、版本不變、更新 `lag` |

**黃燈決定**：同版本時分頁不同只回報 `drift`，不自動改回（避免每天推送默默蓋掉別的管道的改動；要對齊就帶 `reapply:true`）。

**內容指紋不算說明（`note`）**（獨立審查第 1 輪殘餘 d）：營運系統只在節日內容（放假日、補行上班日、排除日）變時升版，來源標題更新（`note`＝「依人事行政總處＋標題」）維持同版；薪資寫分頁本來也不看說明（下面第 2 點）。說明算進指紋會讓「同版只換標題」被當成 `version_conflict`。代價：同版只換標題時分頁的說明欄不會跟著換（說明不進任何計算，只是顯示）。

**寫入順序**：分頁＋稽核（寫鎖內）→ 顯示資料 `PAY_HOL_PUB_VIEW` → 最後才記版本 `PAY_HOL_PUB`。版本紀錄就是「這一版全部寫完」的記號：中途任何一步失敗，版本沒記，同版重送仍當新版本處理（分頁相同不會再改，稽核多一筆「沒有月份要改」），顯示資料與版本會補齊。

### 寫哪些月份

只動集團共用列（`store` 空白）：
1. 2026-05 以前忽略。
2. 本月與未來：紅字天數、加發日不同（或紅字空白／不是數字）→ 改；沒有 → 新增。說明欄不同不算。
3. **已經過去的月份一律不動**：內容不同列在 `skipped_past`，缺列列在 `past_missing`。
   - 跟現行做法的同步同一條規則（2026-11-25 起同步也不補過去缺列）。**後果**：缺列的過去月份算薪會被擋下（`hol_past`），要人工到 `payroll_holiday` 分頁補（系統外處理）；內容不同的過去月份會一直維持舊內容，版本行列出（主管規則「凍結」，已發薪資不變）。
   - 「已經過去」＝月份早於台北時間的本月（`currentYmTaipei()`，跟算薪擋下 `payHolNoRowMsg_` 同一個判斷）。例：12/1～12/10 結算 11 月薪資時，11 月已經算過去。
   - 回應逐月講明拒絕（試推、正式推送、`reapply` 都一樣）：有過去月份沒寫時多三個欄位 `past_code:'hol_past_frozen'`、`past_refused`（＝`past_missing`＋`skipped_past` 排序合併）、`past_message`（白話，例「已經過去的月份不寫入節日資料（整月沒有資料也不補）：2026-09 整月沒有節日資料，不會補上，這幾個月不能在系統裡計算薪資，要人工到薪資試算表的 payroll_holiday 分頁補上（系統外處理）。」）。沒有這種月份時三個欄位都不出現，回應跟以前逐字相同。整份推送照樣 `ok:true`（本月與未來照常寫）；營運系統把它當「有月份沒對齊」處理。
4. 已鎖定：該月有「用集團列的門市」鎖定 → 不改不補，列在 `skipped_locked`。
5. 本店專屬列一律不碰、也不拿來比；`own_rows`＝筆數。
6. 寫鎖內整張寫一次＋稽核 `holiday_publish`＋最後才記版本；拿不到寫鎖回 `busy`。

`skipped_locked`、`skipped_past`、`past_missing` 同時記進版本紀錄的 `lag`，薪資頁版本行（第 4 節 A 版）與 `payroll_master_get`／`payroll_holiday_sync` 的 `hol_pub.lag` 都看得到。**`lag` 不是即時的**：只在正式推送新版本、或同版本帶 `reapply:true` 時重算（試推、同版本沒帶 `reapply` 都不更新）；之後才鎖定的月份、被別的管道補上或改掉的月份，要等下一次推送或重套，版本行才會跟著變。

### 回應

```
{ ok:true, mode, dry_run, version, current, added,
  months_new, months_changed, skipped_locked, skipped_past, past_missing, own_rows,
  changed（正式）| would_change（試推）, drift?（同版本未帶 reapply） }
```
錯誤：`unauthorized`、`scope_forbidden`、`bad_payload`（附 `problems`）、`hol_source_gov`、`version_rollback`、`version_conflict`、`busy`。
稽核：`action='holiday_publish'`、`operator='mini'`（有確認人時「mini（人資主管確認）」）、`reason` 例「營運系統節日表 版本 2027-1（發布 …）：新增 2027-01、…；已鎖定跳過 2026-12；已經過去的月份不動 2026-10」。
